# 20260720_PLAN.md

## 1. Document purpose

This document defines the software-engineering implementation plan for the training and evaluation subsystem of the MLSys LoRA project.

The implementation must support the following experiment pipeline:

```text
experiment YAML
    ↓
load pinned tokenizer and model
    ↓
load and preprocess GSM8K through the existing data module
    ↓
configure Full Fine-tuning or LoRA
    ↓
train under a shared experimental protocol
    ↓
measure GPU memory, non-padding tokens/s, and training time
    ↓
save and reload a final inference artifact
    ↓
generate GSM8K predictions
    ↓
compute deterministic exact match
    ↓
write standardized experiment artifacts
```

The primary research comparison is between Full Fine-tuning and LoRA on a single A40 48 GB GPU, under matched data, effective batch size, precision, training-token budget, and evaluation settings. The required systems metrics are peak GPU memory, non-padding tokens/s, training time, trainable parameter count, checkpoint size, and GSM8K exact match.

This plan deliberately separates:

* reusable Python implementation in `src/`;
* executable command-line programs in `scripts/`;
* HPC resource declarations in `slurm/`;
* experiment declarations in `configs/`;
* runtime artifacts in `results/`, `checkpoints/`, `logs/`, and `data/`.

No command-line script, Slurm logic, sweep submission logic, or one-off utility belongs in `src/`.

## 2. Authoritative requirements

### 2.1 Shared experimental controls

Full FT and LoRA must use exactly the same:

* model and tokenizer revision;
* GSM8K revision and split;
* prompt and tokenization implementation;
* retained examples at a given sequence length;
* maximum sequence length;
* padding policy;
* effective batch size;
* precision;
* attention backend;
* training token budget;
* generation implementation;
* answer parser and exact-match implementation.

The existing data pipeline returns:

```text
input_ids
attention_mask
labels
num_non_padding_tokens
```

The training loop must remove `num_non_padding_tokens` before calling the model and use it for throughput and token-budget accounting.

### 2.2 Existing components that must be reused

The training implementation must import and reuse:

```python
from data.gsm8k import (
    GSM8KDataConfig,
    CausalLMCollator,
    prepare_gsm8k_datasets,
)

from evaluation.generate import (
    generate_predictions,
    save_predictions_jsonl,
)
```

The implementation must not introduce:

* a second GSM8K preprocessing path;
* a second prompt template;
* a second exact-match parser;
* a separate Full FT dataset builder;
* a separate LoRA dataset builder.

### 2.3 Current pinned defaults

The default experiment configuration uses:

## 4. Architectural principles

### 4.1 Thin executable entry points

`scripts/train.py` must only:

1. parse CLI arguments;
2. load a validated configuration;
3. invoke the training library;
4. print the final result;
5. return an appropriate process exit code.

It must not contain:

* the training loop;
* LoRA setup;
* DataLoader construction;
* CUDA memory measurement;
* checkpoint serialization;
* evaluation logic.

### 4.2 One experiment orchestrator

One orchestration object coordinates the complete run:

```text
ExperimentRunner
```

It may call lower-level components, but it must not reimplement their algorithms.

### 4.3 One training engine

The same `TrainerEngine` must execute both Full FT and LoRA.

Differences between the methods must be confined to model parameterization in `src/methods/`.

### 4.4 Explicit contracts

Module boundaries must use typed dataclasses rather than loosely structured dictionaries wherever practical.

YAML dictionaries may exist only at the configuration-loading boundary. After validation, the rest of the implementation must use typed configuration objects.

### 4.5 No hidden storage behavior

The code must not silently:

* copy a model into `models/`;
* materialize a second dataset;
* save intermediate checkpoints;
* upload artifacts;
* delete prior results.

All output paths and persistence decisions must come from configuration.

# 7. Module-level implementation specification

## 7.1 `src/methods/common.py`

This module defines common model-parameter utilities used by Full FT, LoRA, tests, and result reporting.

### `ParameterStats`

```python
@dataclass(frozen=True)
class ParameterStats:
    total_parameters: int
    trainable_parameters: int
    frozen_parameters: int
    trainable_fraction: float
```

Responsibilities:

* represent parameter counts after method configuration;
* provide serializable values for `result.json`;
* avoid recomputing counts in multiple modules.

Invariants:

```text
total_parameters
= trainable_parameters + frozen_parameters
```

and:

```text
0.0 ≤ trainable_fraction ≤ 1.0
```

### `count_parameters(model) -> ParameterStats`

Responsibilities:

* iterate through `model.parameters()`;
* count all parameter elements;
* count parameters where `requires_grad=True`;
* return `ParameterStats`.

It must not modify the model.

### `get_trainable_parameter_names(model) -> tuple[str, ...]`

Responsibilities:

* return the names of all trainable parameters;
* preserve model traversal order;
* support diagnostic logs and LoRA validation.

### `assert_has_trainable_parameters(model) -> None`

Responsibilities:

* raise `ValueError` if no parameters require gradients;
* prevent optimizer construction with an empty parameter list.

### `assert_optimizer_matches_trainable_parameters(model, optimizer) -> None`

Responsibilities:

* collect parameter identities in optimizer parameter groups;
* collect parameter identities where `requires_grad=True`;
* raise an error if a trainable parameter is missing;
* raise an error if a frozen parameter was accidentally added.

This function is primarily a runtime contract check during smoke tests.

---

## 7.2 `src/methods/full_ft.py`

This module is responsible only for configuring and validating Full Fine-tuning.

### `configure_full_finetuning(model) -> ParameterStats`

Responsibilities:

* set `requires_grad=True` for all model parameters;
* return final parameter statistics;
* perform no optimizer construction;
* perform no training.

### `validate_full_finetuning(model) -> None`

Responsibilities:

* assert that all expected model parameters are trainable;
* raise a descriptive error listing the first frozen parameters found;
* call `assert_has_trainable_parameters`.

The function must not assume that parameter names follow a specific architecture.

---

## 7.3 `src/methods/lora.py`

This module injects and validates LoRA adapters.

### `LoraMethodConfig`

The canonical method configuration is defined in `training.config`, but this module may import it for type checking.

Expected fields:

```python
rank: int
alpha: int
dropout: float
target_modules: tuple[str, ...]
bias: str
```

### `resolve_lora_target_modules(model, requested_modules) -> tuple[str, ...]`

Responsibilities:

* verify that every configured target-module suffix exists in the model;
* return the validated target-module tuple;
* reject an empty configuration;
* reject silently ignored target modules;
* include available matching module names in the error message.

The model architecture must not be guessed at runtime without recording the choice.

The initial YAML should explicitly define:

```yaml
method:
  target_modules:
    - q_proj
    - k_proj
    - v_proj
    - o_proj
```

Additional MLP targets may be introduced only as a documented experimental change.

### `configure_lora(model, config) -> tuple[object, ParameterStats]`

Responsibilities:

1. validate rank, alpha, dropout, and targets;
2. create `peft.LoraConfig`;
3. call `get_peft_model`;
4. validate trainability;
5. return the wrapped model and parameter statistics.

The initial LoRA configuration must use:

```text
task_type = CAUSAL_LM
inference_mode = false
```

### `validate_lora_trainability(model) -> None`

Responsibilities:

* ensure at least one trainable parameter exists;
* ensure trainable parameters are adapter parameters;
* ensure base-model parameters remain frozen;
* raise a descriptive error containing unexpected trainable names.

This validation must run before optimizer construction.

---

## 7.4 `src/methods/__init__.py`

This module exposes the method-selection API.

### `configure_training_method(model, config) -> tuple[object, ParameterStats]`

Responsibilities:

* dispatch on `config.method.name`;
* call `configure_full_finetuning` for `full_ft`;
* call `configure_lora` for `lora`;
* reject unknown method names;
* return a consistently shaped result.

No other module should manually branch between Full FT and LoRA setup.

# 8. Metrics modules

## 8.1 `src/metrics/memory.py`

### `MemoryMetrics`

```python
@dataclass(frozen=True)
class MemoryMetrics:
    peak_allocated_bytes: int
    peak_reserved_bytes: int
    peak_allocated_gb: float
    peak_reserved_gb: float
```

### `CudaMemoryTracker`

#### Constructor

```python
CudaMemoryTracker(device: torch.device)
```

Responsibilities:

* require a CUDA device;
* store the target device;
* not reset statistics automatically during construction.

#### `reset() -> None`

Responsibilities:

* synchronize CUDA;
* reset peak allocated and reserved memory statistics;
* establish the start of the measured training region.

It must not call `torch.cuda.empty_cache()` because that changes runtime behavior and is not a measurement operation.

#### `snapshot() -> MemoryMetrics`

Responsibilities:

* synchronize CUDA;
* read maximum allocated memory;
* read maximum reserved memory;
* return both bytes and GiB values.

### `is_cuda_oom(error: BaseException) -> bool`

Responsibilities:

* return true only for recognized CUDA out-of-memory failures;
* avoid classifying arbitrary `RuntimeError` instances as OOM;
* support stable OOM result generation for the batch-feasibility sweep.

## 8.2 `src/metrics/throughput.py`

### `ThroughputMetrics`

```python
@dataclass(frozen=True)
class ThroughputMetrics:
    measured_tokens: int
    measured_seconds: float
    tokens_per_second: float
    warmup_optimizer_steps: int
```

### `ThroughputTracker`

#### Constructor

```python
ThroughputTracker(
    device: torch.device,
    warmup_optimizer_steps: int,
)
```

State:

```text
started
start_time
measured_tokens
warmup_optimizer_steps
```

#### `start() -> None`

Responsibilities:

* synchronize CUDA when using CUDA;
* record `time.perf_counter()`;
* reject a second start call.

#### `record_tokens(non_padding_tokens: int) -> None`

Responsibilities:

* add positive non-padding token counts;
* reject negative counts;
* do nothing before measurement starts.

#### `finish() -> ThroughputMetrics`

Responsibilities:

* synchronize CUDA;
* calculate elapsed time;
* reject finish-before-start;
* return non-padding tokens/s.

The training engine determines when warmup has completed and calls `start()` at that boundary.

Padding tokens must never be included in the numerator.

Responsibilities:

1. open YAML safely;
2. reject empty or non-mapping documents;
3. parse every section;
4. apply only documented defaults;
5. construct typed dataclasses;
6. call `validate_experiment_config`;
7. return an immutable configuration.

### `validate_experiment_config(config) -> None`

Must validate:

```text
experiment.name is nonempty
experiment.sweep is nonempty
model.name is nonempty
model.revision is nonempty
data.revision is nonempty
micro_batch_size > 0
effective_batch_size > 0
gradient_accumulation_steps > 0
effective_batch_size
    = micro_batch_size × gradient_accumulation_steps
learning_rate > 0
weight_decay ≥ 0
num_workers ≥ 0
throughput_warmup_steps ≥ 0
evaluation.batch_size > 0
evaluation.max_new_tokens > 0
```

Stopping conditions:

* smoke configurations may use `max_steps`;
* main experiments may use `training_token_budget`;
* at least one must be set;
* if both are set, training stops at the first condition reached.

Method conditions:

* `full_ft` must not require rank or alpha;
* `lora` requires positive rank and alpha;
* `0 ≤ dropout < 1`;
* `target_modules` must be nonempty.

Precision conditions:

* BF16 availability is checked again at runtime;
* invalid precision names fail during configuration loading.

### `config_to_dict(config) -> dict[str, object]`

Responsibilities:

* convert nested dataclasses and paths into YAML/JSON-safe objects;
* preserve resolved defaults;
* support `resolved_config.yaml` and run metadata.

### `write_resolved_config(config, path) -> None`

Responsibilities:

* create parent directories;
* write the fully resolved configuration;
* use atomic replacement;
* never overwrite a different completed run silently.

# 12. Training engine

## 12.1 `src/training/engine.py`

### `StopReason`

```python
class StopReason(str, Enum):
    MAX_STEPS = "max_steps"
    TOKEN_BUDGET = "token_budget"
    DATA_EXHAUSTED = "data_exhausted"
```

### `TrainingResult`

Defined in `training.results`, but returned by the engine.

### `TrainerEngine`

#### Constructor

```python
TrainerEngine(
    config: ExperimentConfig,
    device: torch.device,
    memory_tracker: CudaMemoryTracker,
)
```

Responsibilities:

* retain immutable training configuration;
* initialize no model or data itself;
* own the training-loop behavior.

#### `_prepare_model_inputs(batch) -> tuple[dict[str, Tensor], int]`

Responsibilities:

1. require `num_non_padding_tokens`;
2. convert it to an integer token count;
3. remove it from model inputs;
4. move tensors to the selected device;
5. return model inputs and token count.

It must reject malformed batches early.

#### `_autocast_context()`

Responsibilities:

* return BF16 autocast for BF16 experiments;
* return a no-op context for FP32;
* avoid FP16 GradScaler logic because FP16 is outside the initial protocol.

#### `_should_stop(optimizer_steps, trained_tokens) -> StopReason | None`

Responsibilities:

* check `max_steps`;
* check `training_token_budget`;
* return the first reached stop condition;
* return `None` otherwise.

#### `_perform_optimizer_step(model, optimizer) -> None`

Responsibilities:

* optionally clip gradients;
* call `optimizer.step`;
* call `optimizer.zero_grad(set_to_none=True)`;
* contain no scheduling behavior.

#### `train(model, train_loader, optimizer) -> TrainingResult`

Algorithm:

```text
model.train()
optimizer.zero_grad(set_to_none=True)
reset CUDA peak-memory statistics

for batches, cycling over the train loader when necessary:
    separate num_non_padding_tokens
    move model inputs to GPU
    enter BF16 autocast when configured
    forward pass
    divide loss by gradient_accumulation_steps
    backward pass
    accumulate raw non-padding tokens

    when accumulation boundary is reached:
        optimizer step
        increment optimizer-step counter
        begin throughput timing after warmup
        record measured tokens after warmup
        test max-step and token-budget conditions

synchronize CUDA
collect memory metrics
finalize throughput metrics
return TrainingResult
```

Requirements:

* `num_non_padding_tokens` must never reach `model.forward`;
* loss must be finite;
* the final partial accumulation window must not be silently treated as a full optimizer step;
* the token budget uses actual non-padding tokens processed;
* the engine must cycle over the dataset for token-budget experiments if one epoch is insufficient;
* the engine must record both micro-steps and optimizer steps;
* all reported training metrics must refer to the same measured region;
* OOM exceptions propagate to the experiment layer for standardized handling;
* non-OOM exceptions must not be converted into successful or OOM results.

# 13. Checkpoint and reload contract

## 13.1 `src/training/checkpoint.py`

The “checkpoint size” metric refers to the final inference-reloadable artifact:

* Full FT: full model plus tokenizer;
* LoRA: adapter plus adapter configuration and tokenizer metadata.

It does not include optimizer state.

### `CheckpointInfo`

```python
@dataclass(frozen=True)
class CheckpointInfo:
    path: Path
    method: str
```

* load the saved complete model;
* use the configured dtype;

LoRA responsibilities:

# 21. Failure handling

## Configuration failure

Behavior:

* fail before model or dataset download;
* print the invalid field;
* write no experiment result directory unless run preparation already began.

## Model or tokenizer failure

Behavior:

* classify as `failed`, not OOM;
* record model name and revision;
* do not silently use fallback.

## Data failure

Behavior:

* classify as `failed`;
* preserve dataset revision;
* do not switch revisions.

## CUDA OOM

Behavior:

* classify only through `is_cuda_oom`;
* write `status="oom"`;
* preserve experiment identity;
* set unavailable metrics to `null`;
* clear references before process exit;
* return exit code 2.

## Non-finite loss

Behavior:

* raise a dedicated training error;
* write `status="failed"`;
* include optimizer and micro-step numbers.

## Checkpoint reload failure

Behavior:

* the run is failed even if training completed;
* no exact-match result is reported as official;
* retain the broken artifact for diagnosis.

## Evaluation failure

Behavior:

* run status is failed;
* training metrics may remain in metadata;
* final result must not claim completion.

# 24. Definition of done

The training system is considered implemented only when all of the following are true:

### Software structure

* [ ] No executable CLI package is added under `src/`.
* [ ] `scripts/train.py` is a thin entry point.
* [ ] Training implementation is importable and unit-tested.
* [ ] Full FT and LoRA use one `TrainerEngine`.
* [ ] Full FT and LoRA use the existing GSM8K pipeline.
* [ ] Full FT and LoRA use the existing evaluation pipeline.

### Configuration

* [ ] All generated experiment YAML files parse.
* [ ] Pinned model and data revisions are passed at runtime.
* [ ] Effective batch arithmetic is validated.
* [ ] LoRA targets are explicit and validated.
* [ ] Resolved configuration is saved per run.

### Training correctness

* [ ] `num_non_padding_tokens` is never passed to the model.
* [ ] Gradient accumulation is correct.
* [ ] Token-budget stopping uses actual non-padding tokens.
* [ ] Full FT updates base parameters.
* [ ] LoRA updates adapter parameters only.
* [ ] Loss remains finite.

### Systems measurements

* [ ] Peak allocated GPU memory is recorded.
* [ ] Peak reserved GPU memory is recorded.
* [ ] Throughput excludes padding tokens.
* [ ] Throughput measurement excludes configured warmup steps.
* [ ] CUDA synchronization bounds timing.

### Artifacts

* [ ] Full FT final artifact reloads.
* [ ] LoRA final adapter reloads with the pinned base model.
* [ ] Checkpoint size is measured consistently.
* [ ] Predictions are retained in JSONL.
* [ ] Result JSON passes the aggregation contract.
* [ ] OOM and implementation failure are distinguished.

### HPC validation

* [ ] LoRA-16 30-step smoke passes on A40.
* [ ] Full FT 30-step smoke passes on A40.
* [ ] Both evaluate the same 32 GSM8K examples.
* [ ] Both produce complete run artifacts.
* [ ] No placeholder results are stored.
* [ ] Both PRs are cross-reviewed.

Only after this definition of done is satisfied may the project proceed to:

1. the main Full FT versus LoRA-16 comparison;
2. the maximum micro-batch sweep;
3. the LoRA rank sweep;
4. the sequence-length sweep;
5. the final three-seed validation.
